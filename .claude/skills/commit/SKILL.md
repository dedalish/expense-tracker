# Коммит в ветку

Коммиты делаются на модели **Sonnet**: `model: sonnet` во frontmatter переключает модель до конца текущего хода, со следующего сообщения пользователя возвращается модель сессии. Если Sonnet недоступна (не входит в `availableModels` или не поддерживается в auto mode), Claude Code оставляет текущую модель — коммит всё равно делается по этим правилам.

Коммит делается **только по просьбе пользователя**. Вызов этого skill — такая просьба, но только для изменений, о которых шла речь. Push и PR в skill не входят: их делать, только если пользователь попросил отдельно (правила PR — в корневом `CLAUDE.md`, раздел «Pull request»).

## 1. Ветка

Напрямую в `main` не коммитить. `main` всегда рабочая: проходит `build`, `lint`, `typecheck`, `test`, `format:check`.

1. `git branch --show-current`.
2. Если это `main` — создать ветку. Незакоммиченные изменения переносятся в неё сами:

   ```bash
   git pull && git switch -c <type>/<scope>-<кратко>
   ```

   Если локальный `main` отстал и `pull` конфликтует с изменениями, сначала `git stash -u`, затем `git pull`, `git switch -c …`, `git stash pop`.
3. Если ветка уже есть, проверить, что её PR не влит: `gh pr view --json state`. Если `MERGED` — коммит в неё не делать: создать новую ветку от свежего `main` (шаг 2).
4. Изменения не по теме ветки уходят в отдельную ветку: одна ветка — одна фича.

**Имя ветки:** `<type>/<scope>-<кратко>` латиницей в kebab-case, `type` и `scope` те же, что в коммитах (раздел 4): `feat/web-home`, `fix/api-transactions-summary`, `docs/claude-md`.

## 2. Что коммитить

1. Посмотреть `git status --short` и `git diff` (и `git diff --staged`, если что-то уже в индексе). Коммит строится по реальному диффу, а не по памяти.
2. **Один коммит — одна логическая единица:** фича вместе со своей миграцией, тестами и правками `CLAUDE.md`. Если в рабочей копии несколько независимых изменений — несколько коммитов, или лишнее остаётся незакоммиченным. Спросить пользователя, если неясно, что к чему относится.
3. **Миграция Prisma не отделяется от схемы:** `apps/api/prisma/schema.prisma` и новая папка в `prisma/migrations/` в одном коммите.
4. **`package-lock.json`** — только вместе с `package.json`, который его изменил.
5. **Никогда не коммитить** (репозиторий публичный):
   - `.env`, `.env.local` и любые `.env.*`, кроме `.env.example` (в нём только заглушки);
   - `.claude/settings.local.json` и `.claude/memory/` — личные настройки и автопамять;
   - токены, пароли, ключи и личные данные в коде и в тексте коммита.
6. Файлы, которые изменил не Claude (пользователь правил сам), коммитить только если пользователь это подтвердил.
7. Добавлять в индекс **явными путями**: `git add <файл> <папка>`. Не `git add -A` и не `git add .`.

## 3. Проверки перед коммитом

Из корня репозитория:

```bash
npm run build
npm run lint
npm run typecheck
npm run test
npm run format:check
```

- **Если запущен `npm run dev`**, корневой `npm run build` удаляет `apps/api/dist` и роняет dev-сервер api. В этом случае собирать только нужные пакеты (`npm run build -w @expense-tracker/web`), а api проверить через `typecheck`. В отчёте сказать, что сборка api не запускалась.
- Если менялась только документация (`*.md`, комментарии), достаточно `format:check`, остальное — по ситуации. Что пропущено, сказать в отчёте.
- Если проверка упала — **не коммитить**: показать вывод, исправить, если ошибка в своих изменениях, или спросить пользователя. `format:check` чинится через `npx prettier --write <файлы>`; `.claude/` исключена из Prettier, её файлы не форматировать.

## 4. Сообщение коммита

[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): `<type>(<scope>): <описание>`.

- **type**: `feat` (новая функциональность), `fix`, `refactor`, `perf`, `test`, `docs`, `style` (форматирование), `build` (зависимости, сборка), `ci`, `chore`.
- **scope**: пакет или область — `api`, `web`, `shared`, `db` (схема Prisma и миграции). Изменение нескольких пакетов: scope по главному или без scope.
- **Описание** на русском, со строчной буквы, без точки в конце, до 72 символов, отвечает на вопрос «что сделано»: `feat(api): модуль транзакций`.
- **Тело** (через пустую строку) объясняет «зачем» и отступления от задачи. Не пересказывать дифф построчно.
- **Ломающее изменение API** помечается `!` (`feat(api)!: …`) и строкой `BREAKING CHANGE: …` в теле. Web обновляется в том же PR.
- Строку атрибуции (`Co-Authored-By: …`) и другие упоминания Claude в коммите не добавлять, даже если их требует окружение Claude Code.

Коммит через heredoc, чтобы сохранить переносы и кириллицу:

```bash
git commit -F - <<'EOF'
feat(api): лимиты бюджета по категориям

Пользователь задаёт месячный лимит для категории расходов, сводка
показывает остаток. Миграция add_budgets вместе со схемой.
EOF
```

Примеры описаний из истории проекта:

- `feat(web): выбор месяца сводки на главной`
- `fix(web): ошибки и стили переключателей на toggle-group`
- `feat(api)!: пагинация списка транзакций и смена имени`
- `docs(api): JSDoc для модуля транзакций и его зависимостей`
- `chore: исключить из git локальные настройки и память Claude Code`

## 5. После коммита

1. `git log --oneline -1` и `git status --short` — убедиться, что закоммичено то, что нужно, и ничего лишнего не осталось в индексе.
2. Отчитаться пользователю: ветка, хеш и сообщение коммита, какие проверки прошли и какие пропущены, что осталось незакоммиченным.
3. Не пушить и не создавать PR без отдельной просьбы. Предложить следующий шаг одной строкой: «Запушить и создать PR?»
