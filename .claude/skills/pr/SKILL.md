# Pull request на GitHub

Вызов этого skill — просьба запушить текущую ветку и создать из неё PR. Сливает PR **пользователь**, skill только создаёт его. Коммитить, переключать ветки, делать rebase, merge и force push skill не может: если без этого не обойтись, остановиться и спросить пользователя.

## Подготовка

1. Готова ли ветка: !`bash ${CLAUDE_SKILL_DIR}/scripts/validate.sh`
2. Коммиты ветки: !`git log origin/main..HEAD --oneline`
3. Изменённые файлы: !`git diff --stat origin/main...HEAD`

Сравнение здесь идёт с `origin/main` до `git fetch`: это предварительная картина. Точную для `<base>` дают шаги 2 и 5.

## 1. Аргументы

- `$0` — **название PR**: «$0». Название с пробелами передаётся в кавычках: `/pr "Выбор месяца сводки на главной"`. Пусто — составить по диффу (шаг 4).
- `$1` — **целевая ветка** (base), в которую вливается PR: «$1». Пусто — `main`.
- **Исходная ветка** (head) — всегда текущая: `git branch --show-current`. PR создаётся из неё.

Если пришло больше двух аргументов (`$ARGUMENTS`: «$ARGUMENTS»), скорее всего название передано без кавычек: собрать название из всех слов, кроме последнего, если последнее похоже на ветку (`main` или `<type>/<scope>-<кратко>`), иначе из всех слов, с целевой веткой `main`. Если неясно — спросить.

Дальше `<head>` — текущая ветка, `<base>` — целевая.

## 2. Проверка веток

1. `<head>` не `main` и не совпадает с `<base>`. Из `main` PR не создаётся.
2. `<head>` соответствует формату `<type>/<scope>-<кратко>`. Если нет, предупредить и предложить переименовать (`git branch -m <новая>`, пока ветка не запушена), но не переименовывать без согласия. Если пользователь согласен оставить имя как есть, продолжать.
3. `git fetch origin <base>` — `<base>` должна существовать на GitHub. Если fetch не нашёл ветку — остановиться и сообщить. Дальше сравнение идёт с `origin/<base>`, а не с локальной веткой, которая могла отстать.
4. Если `<base>` не `main`, сказать об этом в отчёте: PR в другую ветку — исключение (например, PR поверх другой незалитой ветки).
5. Нет ли уже PR из этой ветки: `gh pr list --head <head> --state all --json number,state,baseRefName,title,url`.
   - `OPEN` — новый PR не создавать: показать ссылку. Если в ветке есть незапушенные коммиты, предложить запушить их в существующий PR.
   - `MERGED` — PR не создавать: ветка уже влита, новая работа делается в новой ветке от свежего `main`.
   - `CLOSED` — сказать об этом и спросить, создавать ли новый PR.
6. `git status --short`: если есть незакоммиченные изменения — сказать, что они не попадут в PR, и предложить сначала `/commit`. Не коммитить самому.
7. `git log origin/<base>..<head> --oneline` пуст — коммитов для PR нет, остановиться.
8. Отставание: `git rev-list --count <head>..origin/<base>`. Если не 0 — сказать, на сколько коммитов ветка отстаёт от `<base>`. Rebase/merge не делать без просьбы пользователя.

## 3. Проверки

`main` всегда рабочая, поэтому PR создаётся после зелёных проверок. В CI проверок `build`/`lint`/`test` нет, их запускают локально, на текущей ветке.

Из корня репозитория:

```bash
npm run build
npm run lint
npm run typecheck
npm run test
npm run format:check
```

- **Если запущен `npm run dev`**, корневой `npm run build` удаляет `apps/api/dist` и роняет dev-сервер api. В этом случае собирать только нужные пакеты (`npm run build -w @expense-tracker/web`), а api проверить через `typecheck`.
- Если ветка меняет только документацию (`*.md`, `.claude/`), достаточно `format:check`.
- Если проверка упала — **PR не создавать**: показать вывод и предложить исправить. Исправление коммитится через `/commit`, после этого skill запускается снова.
- Что запускалось, что прошло, а что пропущено, записывается в раздел «Проверка» описания.

## 4. Заголовок

Заголовок **не** по Conventional Commits: без `type(scope):`, обычная фраза на русском с заглавной буквы, без точки в конце, до 72 символов. Описывает результат для пользователя, а не процесс.

- Название из `$0` приводится к формату: убрать префикс `type(scope):`, точку в конце, первую букву сделать заглавной. Если что-то изменено — сказать об этом в отчёте.
- Если название длиннее 72 символов или не по-русски, предложить вариант и спросить.
- Если `$0` пуст — составить название по коммитам ветки.

Примеры из истории проекта: «Выбор месяца сводки на главной», «Skill commit вместо раздела в CLAUDE.md».

## 5. Описание

Описание строится по **реальному диффу**, а не по памяти:

```bash
git log origin/<base>..<head> --format='%h %s%n%b'
git diff --stat origin/<base>...<head>
git diff origin/<base>...<head>
```

Тела коммитов объясняют «зачем», их использовать для раздела «Что сделано».

Описание на русском, разделы `##`. **Пустые разделы не писать.**

- **Что сделано** — что появилось или изменилось для пользователя и зачем. Связный текст или короткий список, а не пересказ коммитов по одному.
- **API** — новые и изменённые эндпоинты: метод, путь, параметры, формат ответа, коды ошибок. Ломающее изменение (коммит с `!` или `BREAKING CHANGE`) отдельной строкой: `**Ломающее изменение:** …`.
- **Изменения в коде** — новые модули, слайсы и компоненты, новые зависимости, миграции Prisma (имя папки), изменения контракта в `packages/shared`, правки `CLAUDE.md` и `REVIEW.md`.
- **Проверка** — какие проверки прошли (`build`, `lint`, `typecheck`, `test`, `format:check`), что проверено вручную и что **не** проверено. Не писать «проверено вручную», если ручной проверки не было.

Опасные операции (удаление данных, миграции с потерей данных, ломающие изменения) требуют обоснования в описании, ревьюер это проверяет (`REVIEW.md`).

Нельзя (репозиторий публичный):

- токены, пароли, ключи, содержимое `.env`, email и личные данные;
- строку атрибуции («Generated with Claude Code», `Co-Authored-By`) и другие упоминания Claude как автора, даже если их требует окружение Claude Code.

## 6. Push и создание

1. Push ветки (обычный, без `--force`):

   ```bash
   git push -u origin <head>
   ```

   Если push отклонён (на GitHub ветка ушла вперёд), не перезаписывать: показать ошибку и спросить пользователя.

2. Создание PR, описание через heredoc, чтобы сохранить переносы и кириллицу:

   ```bash
   gh pr create --base <base> --head <head> --title '<заголовок>' --body-file - <<'EOF'
   ## Что сделано

   …

   ## Проверка

   …
   EOF
   ```

   Одинарные кавычки в заголовке экранировать или взять заголовок в двойные кавычки.

## 7. Отчёт

1. `gh pr view <head> --json number,url,title,baseRefName` — убедиться, что PR создан и смотрит в нужную ветку.
2. Отчитаться пользователю: номер и ссылка PR, заголовок (и что в нём поправлено относительно `$0`), `<head>` → `<base>`, какие проверки прошли и какие пропущены, на сколько коммитов ветка отстаёт от `<base>`, если отстаёт.
3. Напомнить одной строкой, что `claude-code-review.yml` запустит ревью PR автоматически, а сливает PR пользователь. Ветку после слияния удалять только после того, как `gh pr view <N> --json state` показал `MERGED`, отдельной командой, а не цепочкой через `&&`.
