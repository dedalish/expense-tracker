# Тест на файл

Вызов этого skill — просьба написать тест на переданный файл. Skill создаёт или дополняет **только** `*.spec.ts`. Тестируемый код он не меняет: если без правки кода тест не написать (функция не экспортируется, зависимость создаётся внутри и не подменяется) или тест нашёл ошибку, остановиться и спросить пользователя. Новые зависимости (`@testing-library/*`, `jsdom`) без согласия не ставить. Коммитить, пушить и переключать ветки skill не может, коммит делается через `/commit`.

## 1. Аргументы

- `$0` — **файл**, на который пишется тест: «$0». Путь от корня репозитория или от пакета (`apps/api/src/categories/categories.service.ts`, `src/shared/lib/month.ts`). Пусто — спросить, какой файл покрыть.
- Остальные слова (`$ARGUMENTS`: «$ARGUMENTS») после пути — **что проверить**: конкретная функция, сценарий или ошибка. Пусто — покрыть всё публичное поведение файла (шаг 4).

Если путь не найден как есть, поискать файл по имени (Glob `**/<имя>`, без `node_modules`, `dist`, `.next`, `src/generated`). Нашлось несколько — спросить, какой.

Дальше `<file>` — путь к файлу от корня, `<spec>` — путь к тесту, `<pkg>` — пакет (`api` или `web`).

## 2. Проверка файла

1. `<file>` существует и это исходник на TypeScript (`.ts`, `.tsx`).
2. `<file>` не тест (`*.spec.ts`), не сгенерированный код (`apps/api/src/generated/`, `next-env.d.ts`) и не миграция. Тест на такой файл не пишется: сказать и остановиться.
3. Определить пакет и куда ляжет тест:
   - `apps/api/src/...` — `<pkg>` = `api`, `<spec>` рядом с файлом: `<имя>.spec.ts`.
   - `apps/web/src/...` — `<pkg>` = `web`, `<spec>` рядом с файлом: `<имя>.spec.ts`.
   - `packages/shared/src/...` — в shared нет Vitest. Схемы shared тестируются в api: `<pkg>` = `api`, `<spec>` в модуле api, который использует схему, по образцу `apps/api/src/transactions/transaction.schemas.spec.ts` (импорт из `@expense-tracker/shared`). Если в api ещё нет модуля для этой схемы — спросить, куда положить тест.
   - `apps/web/app/...` (тонкие `page.tsx`/`layout.tsx`/`route.ts` с реэкспортом) — тестировать нечего: сказать, что логика лежит в `src`, и предложить файл оттуда.
4. **Что можно тестировать в web.** Vitest в web работает в окружении `node`, без DOM. Тестируются чистые функции (`lib`-сегменты слайсов, `shared/lib`, `config`). Если `<file>`:
   - React-компонент (`.tsx`, `'use client'`) — DOM-тестов в проекте нет: предложить вынести логику в `lib` и покрыть её, или спросить, ставить ли `@testing-library/react` и `jsdom`;
   - `server-only`, Server Action или код с `next/headers`/`next/cache` — сказать, что такие модули пока не тестируются, и спросить, мокать ли их через `vi.mock` или покрыть только чистые функции из файла.
5. `<spec>` уже есть — не перезаписывать: прочитать его и **дополнить** недостающими случаями, существующие тесты не менять без просьбы.
6. `git branch --show-current`: если это `main`, предупредить, что тест попадёт в рабочую копию `main`, а ветку создаст `/commit` (`test/<pkg>-<кратко>`). Работу не прерывать.

## 3. Изучение кода

Тест строится по **реальному коду**, а не по названию файла:

1. Прочитать `<file>` целиком: экспорты, ветвления, бросаемые исключения, граничные значения, коды ошибок.
2. Прочитать `CLAUDE.md` пакета (`apps/api/CLAUDE.md` или `apps/web/CLAUDE.md`), если он ещё не загружен: раздел «Тесты» / «Стек и тесты» и описание модуля, которому принадлежит файл. Описанное там поведение (404 на чужую запись, 409 при удалении, сумма строкой, дата `YYYY-MM-DD`) — главные кандидаты в тесты.
3. Прочитать типы и схемы, которые использует файл: Zod-схемы из `packages/shared/src`, модели из `apps/api/prisma/schema.prisma`, интерфейсы репозиториев.
4. Прочитать образец теста того же вида (Glob `apps/<pkg>/src/**/*.spec.ts`) и повторить его стиль:
   - сервис или хендлер api с зависимостями — `src/users/commands/update-user-name.handler.spec.ts`, `src/transactions/transactions.service.spec.ts`;
   - guard, pipe — `src/auth/auth.guard.spec.ts`, `src/common/zod-validation.pipe.spec.ts`;
   - схемы shared — `src/transactions/transaction.schemas.spec.ts`;
   - чистые функции web — `src/shared/lib/month.spec.ts`, `src/widgets/transactions-list/lib/search-params.spec.ts`.

## 4. Что покрывать

Если в аргументах указано, что проверить, — начать с этого, остальное по ситуации. Иначе покрыть **публичное поведение** файла:

- основной сценарий каждой экспортируемой функции или публичного метода;
- каждую ветку с ошибкой: какое исключение (`NotFoundException`, `ConflictException`, `BadRequestException`, `UnauthorizedException`) и в каком случае;
- граничные значения: пустая строка, `undefined`, пределы (`pageSize` 100, страница за пределами данных), неверный формат (дата, месяц, UUID);
- предметные правила из `CLAUDE.md` пакета: доступ только к своим записям, суммы через `Prisma.Decimal` и строкой в JSON, даты полночью UTC;
- для зависимостей — что их вызвали с нужными аргументами (`toHaveBeenCalledWith`), и что не вызвали, когда не должны (`not.toHaveBeenCalled`).

Не тестировать: приватные методы напрямую, детали реализации (порядок внутренних вызовов, если он не важен), сгенерированный код, сам Prisma, Nest и Zod.

## 5. Как писать

Общее:

- Vitest, импорт явный: `import { describe, expect, it, vi } from 'vitest';`.
- Названия `describe` — имя класса или функции, названия `it` — **на русском**, со строчной буквы, описывают поведение: `'возвращает null, если пользователя нет'`, `'отклоняет %j'`.
- Похожие случаи — через `it.each`, а не копированием.
- Тестовые данные — константы вверху файла (UUID вида `0199a1b2-c3d4-7e5f-8a9b-0c1d2e3f4a5b`, даты `new Date('2026-01-01T00:00:00.000Z')`, email `ivan@example.com`). Реальные email, токены и пароли не использовать.
- Даты и «сейчас» — фиксировать (`vi.useFakeTimers()` + `vi.setSystemTime(...)`, в конце `vi.useRealTimers()`), если результат от них зависит.
- Тест не ходит в сеть и в базу.

**api** (`apps/api/CLAUDE.md`, раздел «Тесты»):

- `Test.createTestingModule` не используется. Тестируемый класс создаётся через `new`, зависимости — объекты с `vi.fn()` в функции `setup()`, приведённые через `as unknown as <Тип>`. `setup()` возвращает класс и моки, каждый тест вызывает его заново.
- Относительные импорты **с `.js`** (`./categories.service.js`), клиент Prisma — из `../generated/prisma/client.js`.
- Ошибки Prisma — через `new Prisma.PrismaClientKnownRequestError('…', { code: 'P2025', clientVersion: 'test' })` с нужным кодом (коды в `src/common/prisma-errors.ts`).
- Для `CommandBus`/`QueryBus` мокается `execute`, проверяется класс и поля переданной команды или запроса (`expect.any(GetCategoryQuery)` или `toHaveBeenCalledWith(new GetCategoryQuery({ … }))`).
- Декораторы и метаданные (guard) — `import 'reflect-metadata';` первой строкой.

**web** (`apps/web/CLAUDE.md`, раздел «Стек и тесты»):

- Импорт тестируемого кода внутри слайса — относительный (`./month`), из других мест — через алиас `@/...`, без расширения.
- Окружение `node`: `window`, `document` и React-рендеринг недоступны.

## 6. Запуск и проверки

Из корня репозитория, путь к тесту — от папки пакета (`src/...`):

```bash
npm run test -w @expense-tracker/<pkg> -- <spec от пакета>
npx prettier --write <spec>
npm run lint -w @expense-tracker/<pkg>
npm run typecheck -w @expense-tracker/<pkg>
```

- Тест должен **пройти**. Если падает:
  - ошибка в самом тесте (неверный мок, импорт, ожидание) — исправить тест и запустить снова;
  - тест показывает ошибку в `<file>` (поведение расходится с `CLAUDE.md`, схемой или очевидным смыслом) — код **не править**: показать падающий случай и вывод, объяснить, в чём расхождение, и спросить пользователя. `it.skip`/`it.todo`, чтобы скрыть падение, не ставить.
- `lint` и `typecheck` должны пройти. Ошибки в `<spec>` исправить, ошибки в других файлах — только сообщить.
- Весь набор тестов пакета (`npm run test -w @expense-tracker/<pkg>`) запустить в конце, чтобы убедиться, что новый тест не мешает остальным.

## 7. Отчёт

1. `git status --short` — убедиться, что изменён или создан только `<spec>`.
2. Отчитаться пользователю:
   - `<spec>` — создан или дополнен, сколько тестов добавлено;
   - что покрыто, списком по функциям или сценариям, одной строкой на пункт;
   - что **не** покрыто и почему (нужен DOM, `server-only`, требуется правка кода);
   - результаты: тест, весь набор пакета (число тестов), `lint`, `typecheck`, формат;
   - найденные расхождения в коде, если есть.
3. Предложить следующий шаг одной строкой: «Закоммитить через `/commit`?» (тип коммита `test`, scope — пакет: `test(api): тесты сервиса категорий`).
